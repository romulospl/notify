# Runbook: incidents

It covers the five real alerts from the external monitoring ([`alerts.yml`](../../infra/monitoring/prometheus/rules/alerts.yml), [ADR 0005](../adr/0005-external-monitoring.md)) and an outage of the portal or of web ingestion. The `Watchdog` alert is an always-on heartbeat, not an incident; if it **stops arriving** at the external service configured in `DEADMAN_URL`, the problem is the monitoring host (see `ProberDown`).

## Initial triage (applies to all)

1. Look from outside, from any machine (commands from step 3 ("Check production") of [`docs/deploy.md`](../deploy.md)):

   ```bash
   curl -fsS https://<portal_host>/api/health           # portal: {"ok":true}
   curl -fsS https://<ingest_host>/healthz               # gateway (503: Postgres or Umami down)
   curl -fsS https://<ingest_host>/healthz/stack         # stack check on the VPS
   curl -fsS "https://<ingest_host>/c?s=00000000-0000-4000-8000-000000000000"
   ```

2. Log in to the VPS, go to the checkout folder and look at the state:

   ```bash
   docker compose -f prod.yaml ps
   df -h /srv/stellytics
   ```

3. If not even SSH gets in, the VPS is down: look at the provider's console (restart, check the disk). The data lives in `STELLYTICS_DATA_DIR` (default `/srv/stellytics`). To recreate the VPS: `init.sh` and `deploy.sh` ([`docs/deploy.md`](../deploy.md)) and the restore if the data was lost ([backup and restore](backup-and-restore.md)).

## EndpointDown

**Symptoms.** Email `<component> is down`: the target (portal, web gateway or API ingestion) went 1 minute without the expected response.

**Diagnosis.**

- Which component? It is in the `component` label of the email. If only one is down, the problem is in its service; if all are down, it is the VPS, Caddy or the network.
- On the VPS: `docker compose -f prod.yaml ps` (look for `unhealthy`, `restarting` or missing) and `docker compose -f prod.yaml logs --tail 200 <service>`.
- The proxy is the Compose Caddy service; it forwards over the Docker network to `portal`, `ingest-web` and `collector`. In Compose, `ingest-web` depends on `postgres`, `umami` and `portal`; `collector` and `rollup` depend on `postgres` and `portal`; `portal` and `umami` depend on `postgres`. Start with the deepest one that is bad (usually `postgres`: `df -h /srv/stellytics`, a full disk takes everything down).
- Through Prometheus on the monitoring host (tunnel `ssh -N -L 9090:127.0.0.1:9090 -L 9093:127.0.0.1:9093 root@<monitor-host>`, then `http://127.0.0.1:9090`): the `probe_success` query and the *Status → Targets* page show which target is failing.

**Action.**

- Service stopped or `unhealthy`: `docker compose -f prod.yaml up -d --wait` (recreates whatever is missing) or `docker compose -f prod.yaml restart <service>`.
- A new version that broke things: move the checkout back to the previous commit (or, if you use release images, `PORTAL_IMAGE` etc. back to the previous digests in `.env.production`) and run `sudo ./deploy.sh` again (see `docs/deploy.md`; the rollback does not undo a database migration).
- Full disk: look at `docker system df` and `du -sh /srv/stellytics/*`; restore leftovers and old images are the candidates. **`postgres.before-*` is only deleted after a checked restore** ([backup and restore](backup-and-restore.md)). `docker image prune` (without `-a`) removes only dangling images; **never** run `docker system prune --volumes`. Growing the disk is done through the VPS provider.
- The portal comes up but the dashboard shows no data or does not create sites: check whether Umami responds (`docker compose -f prod.yaml ps umami`) and whether `UMAMI_API_KEY` is valid (see [secret rotation](secret-rotation.md), effect of `umami_app_secret`).
- The gateway answers `204` but the events do not show up on the dashboard: `204` is also the response for a refused site and for an invalid proof (on purpose). Check the site on the project screen (active and not archived) and `docker compose -f prod.yaml logs ingest-web`.

**Verification.** The same triage from outside responds; `docker compose -f prod.yaml ps` with everything `healthy`; the resolved email arrives (`send_resolved: true` in the `alertmanager.yml` generated by `configure.sh`; the actual delivery was not observed).

**Data loss.** While `ingest-web` or Umami are down, incoming web events are dropped; there is no queue. Record the incident window.

**Escalate** if: the disk or the VPS has a provider fault (provider support); Postgres does not come up and the log indicates corruption (see [backup and restore](backup-and-restore.md)); or the incident goes past 1 hour without a cause.

## StackUnhealthy

**Symptoms.** Email `The production stack check is failing`: for 5 minutes `/healthz/stack` has been answering 503, because the check that runs every minute on the VPS ([`stack-check.py`](../../infra/scripts/stack-check.py), `stellytics-check.timer`) failed. The public endpoints may be up; the problem is something that can only be seen from inside.

**Diagnosis.** On the VPS, `journalctl -u stellytics-check -n 20 --no-pager` shows the reason, one line per failure:

- `<service>: exited`, `unhealthy` or `not created`: follow the `EndpointDown` diagnosis. `rollup: unhealthy` means the 1m → 1h → 1d rollup stopped (`docker compose -f prod.yaml logs --tail 100 rollup`); without it, the API dashboards lose the 24-month aggregates.
- `postgres: WAL archiving is failing` or `backup: ...`: [backup and restore](backup-and-restore.md). Unarchived WAL also fills the disk.
- `disk: ... full`: the full-disk action from `EndpointDown`.
- `check failed: ...`: the check itself did not run (Docker stopped, Postgres not responding, S3 timeout). See `systemctl status stellytics-check.service`.
- No new line in the journal: the timer stopped (`systemctl list-timers stellytics-check.timer`). `/healthz/stack` keeps the last green result while the `status/stack-ok` file exists; run `sudo ./deploy.sh` to reinstall the timer.

**Action.** Fix the cause and run the check right away: `systemctl start stellytics-check.service`.

**Verification.** `curl -fsS https://<ingest_host>/healthz/stack` answers `ok` and the alert resolves.

## TLSCertificateExpiringSoon

**Symptoms.** A target's certificate expires in less than 14 days; Caddy's automatic renewal may be failing.

**Diagnosis.**

- `docker compose -f prod.yaml logs --since=24h caddy`; the persistent state lives in `/srv/stellytics/caddy`.
- DNS: `dig +short <portal_host>`, `dig +short <ingest_host>` and `dig +short <api_host>` must point to the VPS (A and AAAA).
- Port 80 open from outside: `nc -vz -w3 <vps-ip> 80` (the Let's Encrypt HTTP-01 challenge goes through it; the VPS firewall, configured by the operator, must open 80 and 443).
- Caddy issues a certificate for each host in the `Caddyfile` (`PORTAL_HOST`, `PORTAL_ALIAS_HOST`, `INGEST_HOST` and `API_HOST`) and stores them in `/srv/stellytics/caddy`.
- Check that the container is running: `docker compose -f prod.yaml ps caddy`.

**Action.** Fix DNS/firewall and confirm that 80/443 reach the VPS. Caddy tries to issue and renew automatically; follow `docker compose -f prod.yaml logs -f caddy`.

**Verification.** `echo | openssl s_client -connect <portal_host>:443 -servername <portal_host> 2>/dev/null | openssl x509 -noout -enddate` shows a new date; the alert resolves (it has `for: 1h`).

**Escalate** if fewer than 3 days are left: an expired certificate takes down the portal, ingestion and the API. If Let's Encrypt is down, wait for their status.

## ProbeFailing

**Symptoms.** `<component> is not being checked`: Prometheus cannot even ask the blackbox to test that target (`up{job="endpoints"} == 0`). The real state of the target is unknown, and `EndpointDown` does not fire.

**Diagnosis.** On the monitoring host (`cd infra/monitoring` in the checkout): `docker compose ps`, `docker compose logs --tail 100 prometheus blackbox`. Look for an error about a nonexistent module in `blackbox/blackbox.yml` or about the configuration after running `configure.sh`. Test the target by hand through Prometheus (tunnel above) in *Status → Targets*.

**Action.** Restore the configuration from the repository: update the checkout, run `infra/monitoring/configure.sh <env-file>` and `docker compose up -d --wait` in `infra/monitoring/` (restart `prometheus` and `alertmanager` if the configuration is not reloaded). Meanwhile, do the triage from outside by hand.

**Verification.** *Status → Targets* with the target `UP` and `probe_success` equal to `1`.

**Escalate** if the configuration fails repeatedly: the monitor is the only external watch.

## ProberDown

**Symptoms.** `The blackbox prober is down`: the blackbox exporter does not respond and no target is tested. This alert covers **only the blackbox**. Because of the Alertmanager `inhibit_rule` (in the `alertmanager.yml` generated by `configure.sh`), while it is active, `EndpointDown` and `ProbeFailing` are suppressed: do not expect those emails, and the real state of production is unknown; do the triage from outside by hand.

**And if the whole monitoring host goes down?** No alert fires, because Prometheus and Alertmanager live on it. The only clue is the **external heartbeat** (`Watchdog` sent to `DEADMAN_URL`) no longer arriving, and **only if `DEADMAN_URL` is set**: without it the Watchdog goes to the `blackhole` receiver and nobody finds out.

**Diagnosis.** On the monitoring host (`cd infra/monitoring` in the checkout): `docker compose ps` (services `prometheus`, `blackbox` and `alertmanager`), `docker compose logs --tail 100 blackbox`. If SSH does not get in, the host is down: provider console.

**Action.** `docker compose up -d --wait` in the monitor folder; if the host went down, restart it from the console (a restart of the stack after a real reboot was not checked). To recreate from scratch, clone the repository and run `infra/monitoring/configure.sh <env-file>` and `docker compose up -d --wait`.

**Verification.** `probe_success` goes back to `1` and `ProberDown` resolves.

**Escalate** if the monitor host is lost: production carries on, unwatched; recreate it on a new host with `configure.sh` (`docs/deploy.md`, "Monitoring").
